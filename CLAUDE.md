## Project Overview

A custom Power BI visual ("Toggle Slicer"): a **single toggle or a group of two-state (on/off) toggles**, one row per bound field, each driving its own DAX-based filter in Power BI reports. Rows can be drawn as sliding switches, checkboxes or radio buttons, inside a container with a flat/embossed/sunken border, and the group can enforce rules (Only one active, Master switch, Group enable). It replaces a stack of standard slicers styled to look like switches, giving a cleaner, purpose-built end-user control for a pattern that gets reused across multiple reports.

The visual's GUID (`toggleSlicer…`, in `pbiviz.json`) is permanent once published to AppSource - never change it. Test new versions locally with Developer mode instead, and keep property/object names in `capabilities.json` stable once released, since renaming one drops the value saved in existing reports.

Only the `toggle` data role (well name "Toggles") is required: one bound column is a single toggle (a group of one), which is what the landing page's "One toggle" tab sets up.

## How It Works

The whole group is **one** disconnected table with **one On/Off column per toggle**; each column's name becomes that row's name:

```
Toggle Group Table =
CROSSJOIN(
    DATATABLE("Toggle 1", STRING, {{"On"}, {"Off"}}),
    DATATABLE("Toggle 2", STRING, {{"On"}, {"Off"}}),
    DATATABLE("Toggle 3", STRING, {{"On"}, {"Off"}})
)

Toggle 1 State =
IF(
    SELECTEDVALUE('Toggle Group Table'[Toggle 1]) = "On",
    1,
    0
)
```

The `toggle` data role (well name "Toggles") accepts up to 12 fields - Power BI shows a fresh empty slot below each one dropped in, which is what makes the well "dynamic". An optional `groupEnable` role (max 1) takes a Group enable field built the same way. Both roles feed one categorical mapping via `categories.select`, and each column's `source.roles` says which role it came from.

Clicking writes **real slicer-style basic filters** via `host.applyJsonFilter(filters[], "general", "filter", FilterAction.merge)` - one `IN {value}` filter per bound field, the whole group's set written at once (general.filter holds a single array for the visual). State is read back from `options.jsonFilters` on every `update()`, matched to rows by filter target (table + column). This is what keeps each row DAX-readable, bookmarkable and syncable. **The visual is a rendering layer over filters - it does not use `persistProperties` for state, because that would not be readable by DAX.** An Off row applies its Off value rather than clearing its filter, because the bridge pattern (README → Tables and bridges) maps the Off row to every member.

Why `CROSSJOIN`: the table must hold **every combination** of On/Off values, so a filter on one column never constrains another - filtering "Toggle 1" to On still leaves both values of every other column. (A two-row table with several columns would tie them together.) The visual's own query over several columns therefore returns every combination (2^N rows - the table's own rows when they share a table, or a query-time cross join if a report author binds columns from unrelated tables, which also works), so `parseColumn()` de-duplicates each column on its own rather than reading rows. The 12-field cap keeps that small (2^13 = 8192 rows with Group enable, under the 10000-row `dataReductionAlgorithm`). The bridge pattern (README → Tables and bridges) keys a single shared bridge on a combination-key column, since one group table can only have one active relationship path to a given dimension.

The bound column's two values don't have to be literally "On"/"Off" text — `ON_VALUES`/`OFF_VALUES` in `visual.ts` (matched case-insensitively, trimmed, via `normalize()`) also accept `"true"`/`"false"` and `"1"`/`"0"`. Each column is validated independently (exactly two distinct values - counted both raw and normalized, so case variants like `"On"`/`"ON"` in one column are rejected rather than half-filtered - one On alias, one Off alias), so columns in one group can use different conventions. A one-column table (`DATATABLE("Toggle", STRING, {{"On"}, {"Off"}})`) is simply a group table with one toggle.

## Format pane layout

Seven cards, ordered from the outside in. Each is one `capabilities.json` object with the same name; composite cards split into named groups, and an on/off feature is the card's (or group's) own header toggle (`topLevelSlice`), so the pane has no separate "Show x" row to hunt for.

| Card (object) | Groups / contents |
|---|---|
| Toggle Group (`toggleGroup`) | Layout (`rowAlignment`, `rowSpacing`, `indent`, `verticalAlignment`) · Background - header toggle `showBackground` (`backgroundColor`) · Border (`borderStyle`, `borderColor`, `borderWidth`) · Corners & padding (`cornerRadius`, `padding`) |
| Toggle Group Label (`groupLabel`) | Header toggle `show`; Text (`text`, `position`, `alignment`, `spacing`, font, `fontColor`) · Background · Border · Corners & padding |
| Toggle (`toggleControl`) | Style (`controlStyle`, `depthEffect`) · Colors (`onColor`, `offColor`) · Size (`sizeMode`, `minHeight`, `maxHeight`, `fixedHeight`) · Border · Corners & padding. No Background group: its fill is the Colors |
| Handle (`handle`) | Color (`backgroundColor`, always on) · Border · Corners & padding |
| Toggle Label (`toggleLabel`) | Header toggle `show`; Text (`position`, `spacing`, font, `fontColor`) · Background · Border · Corners & padding |
| State Label (`stateLabel`) | Header toggle `show`; Text (`onText`, `offText`, `position`, `spacing`, font, `fontColor`) · Background · Border · Corners & padding |
| Group Behavior (`behavior`) | `onlyOneActive`, `masterSwitch`, `masterLabel` |

The layers are called **Toggle Group, Toggle Group Label, Toggle, Handle, Toggle Label and State Label** everywhere - Format pane, docs, code comments. Power BI's own General → Title and General → Background are separate ("Title"/"Background"); the Toggle Group Label and the Toggle Group's Background are drawn by this visual.

Rules for changing it: display names use US spelling ("color"); a property that only matters in one state is hidden in the card's `onPreProcess()` rather than left as a dead control; property names are unique within a card but repeat across cards (`show`, `spacing`, `fontColor`, and the shared box properties); every layer but Group Behavior keeps the same four box settings (see Layer boxes below); and once the visual is published, renaming an object or property drops the value saved in existing reports, so add rather than rename.

## Implementation Notes

- Keep formatting (colours, labels) in `capabilities.json` `objects` and read them via `dataView.metadata.objects` in `update()` — don't hardcode colours in `visual.ts`, so users can theme it per-report from the Format pane.
- Handle the "no filter yet" render state (first load, or a field newly added to the well) by matching how the starter DAX reads an unfiltered column: toggles render **Off** (`SELECTEDVALUE(...) = "On"` is false with both values in play), the Group enable row renders **On** (`<> "Off"`, so a new group isn't born disabled) - see `readStatesFromFilters()`. The starter DAX deliberately compares values instead of relying on `SELECTEDVALUE`'s fallback argument, so the two can't drift apart.
- The `dataReductionAlgorithm` is capped at 10000 rows, not 2 per field — it has to hold the full cross join (see How It Works), and a mis-bound field (e.g. a real column with several distinct values) must still surface its extra values so `parseColumn()` rejects it rather than silently truncating it to two.
- **Toggle group model:** `this.items: GroupItem[]` is rebuilt on every `update()` in display order — the Group enable row (`kind: "enable"`, level 0), then the visual-only master row (`kind: "master"`, no field/filter/identity), then one `kind: "toggle"` row per field, each level one deeper than the headers above it. Toggles are ordered by the undocumented-in-typings `source.rolesIndex.toggle[0]` (well position) when the host supplies it, falling back to data view order; a field dropped in twice - or into both Group enable and Toggles - is de-duplicated by filter target (table + column), Group enable winning, so no two rows ever write conflicting filters for one column. Rows' DOM is a pool (`ensureRowPool()`) reused across renders so keyboard focus survives the re-render that follows each click; event handlers look their `GroupItem` up by index at event time.
- **Group behavior** (`handleClick()`; the `behavior` card), always written as one `applyStates()` call covering every field: **Only one active** leaves at most one child On after *every* click, even if the group arrived with several On (e.g. the rule was switched on afterwards): turning one On keeps just it, turning one Off clears the group, and a radio-skinned row can't be clicked Off (native radio behaviour) - clicking an On radio only clears any others still On; **Master switch** sets every child to the opposite of the master's current state (Mixed counts as Off, so a Mixed master turns all On) - under Only one active it instead turns On just the first child, and `updateMasterState()` reads On as "any child On" rather than "all"; **Group enable** flips only itself - `isDisabled()` makes every other row (master included) greyed out, `aria-disabled`, out of the tab order and click-inert, while its state and filter stay untouched (per the requirement "disabled, not turned off"). Measures gate on the enable field themselves (README → Group enable table).
- **Stale filters:** a field removed from the well leaves its filter in `general.filter`, invisibly filtering the report. `cleanUpStaleFilters()` rewrites the set for the bound fields when it sees an unknown target (or, when the last field is removed and the landing page shows, clears `general.filter` with `FilterAction.remove`), once per distinct stale set *and* bound set (`lastStaleCleanup`, so a group that changes while the same stale filter lingers is retried; reset whenever an update finds nothing stale, so the same filter reappearing later - a bookmark, Sync slicers, the same field removed again - is cleaned too) so a host that doesn't echo the result can't loop `update()`, and never when interactions are disallowed.
- **Row layout:** one CSS grid (`.toggle-group`) with rows as `display: contents`, so names and toggles line up in two columns across the whole group. Name position is swapped in **DOM order** by `render()`, not CSS `order` (which would reorder cells across rows in a shared grid). Indent (`--toggle-level` × `--toggle-indent`) goes on whichever cell comes first; with names on the right, each name also gets a negative margin of `(level - maxLevel) × indent` so a header's name hangs beside its own toggle rather than lining up with its children's. Hidden names switch the grid to one column (otherwise cells from different rows would pair up). `toggleGroup.rowAlignment` other than Left adds `is-group-stretched` to titleWrapEl so the group spans the container's full width (it also resets titleWrapEl's auto margins — a cross-axis auto margin beats `align-self: stretch`); within that width, Center/Right set the grid's `justify-content` to `center`/`end`, and Justify makes one column `1fr`. Without the stretch, a shrink-wrapped group has no spare room, so Center/Right would silently do nothing. With an Inline title (`groupLabel.position` inline-left/right) the stretched group fills the row *beside* the title, so Center/Right/Justify align the rows within that remaining space rather than the full frame - deliberately, since aligning against the full frame would put the rows underneath the title - and Toggle Group Label → Alignment then has no free space left to move the title into (the same trade-off Justify always had). With the default Above title, the two alignments stay fully independent.
- **Toggle Group box:** `frameEl` (`.toggle-group-frame`) is the box around label + rows, filling the tile and scrolling on overflow; its Background, Border, Corner radius and Padding are the shared layer box (see Layer boxes). An Embossed frame adds a 4px margin so its outer drop shadow isn't clipped by the visual's own bounds. Vertical alignment uses auto margins on titleWrapEl, not `justify-content`, since centred overflowing content can't be scrolled back into view. `showSection()` shows/hides `frameEl`.
- **High contrast:** `applyColors()` in `visual.ts` checks `host.colorPalette.isHighContrast` and, when active, substitutes the theme's `foreground`/`background`/`foregroundSelected` colours for the user's chosen on/off colours (via CSS custom properties), since custom Format-pane colours aren't guaranteed to be legible in high-contrast themes. `applyContainer()` likewise swaps the container border to `foreground` and drops its fill, and `applyFonts()` forces every font colour to `foreground`.
- **On colour follows the theme by default:** `toggleControl.onColor`'s value in `settings.ts` (`#2ECC71`) is only the fallback used before a report author ever touches the swatch. `applyColors()` checks the raw `dataView.metadata.objects.toggleControl.onColor` (not the populated settings model, which always has *some* value and can't distinguish "never set" from "explicitly set to the default") — when it's absent, the effective On colour is `host.colorPalette.getColor("toggleOnColor").value` instead, i.e. the report theme's first data colour, matching the "Color 1" swatch under Format → Theme → Colors. This is the only `getColor()` call this visual makes, so it deterministically resolves to palette index 0 rather than round-robining to a later theme colour.
- **Layer boxes:** every layer but Group Behavior has the same Background / Border (None, Flat, Embossed, Sunken) / Corner radius / Padding, built by `BoxSlices` in `settings.ts` - so the property names and the `Visual_Box_*` localization keys are shared - and applied two ways. The values are CSS custom properties on the root, one prefix per layer: `--grp-*` (Toggle Group), `--gl-*` (Toggle Group Label), `--tl-*` (Toggle Label), `--sl-*` (State Label), each `-bg`/`-bw`/`-bc`/`-radius`/`-padding`, written by `setBoxVars()`; the border *style* is a class on each element (`is-border-flat`/`-embossed`/`-sunken`, none = no class) via `setBorderStyle()`. `visual.less`'s `.layer-box(@p)` mixin turns both into CSS. A "toggle"-mode box (group and the label layers) has a Background header toggle, off by default; the Handle's is a plain always-on colour; the Toggle has none (its fill is On/Off colour). The Toggle Group's Background is separate from Power BI's own General → Background, which every visual gets and this code can't touch - the setting's description says so, or a report author toggling one while looking at the other would conclude the control is broken. Embossed and Sunken are fixed `rgba()` shading over the report author's own colour/width (no `color-mix()`, which needs a newer Chromium than every managed WebView2/Edge install has). High contrast swaps every border to the theme foreground and drops every fill. Per-row elements (toggle labels, tracks, handles, state label boxes) get their style class in `render()`/`renderSwitch()`. The Toggle and Handle can't use the mixin because their size is tied to the toggle's height - see Toggle border, padding and radius.
- **Sync slicers / Filters pane:** `capabilities.json` declares a `general.filter` object plus `supportsSynchronizingFilterState: true` — the same contract native slicers use (the flag was documented but missing before the group conversion). The group writes an *array* of per-column filters to that one property; sync behaviour with several filtered columns still needs confirming in Power BI (Todo 6).
- **Landing page vs. validation message:** `update()` distinguishes "nothing bound to Toggles yet" (landing page, via `supportsLandingPage: true` - a Group enable field alone still shows it) from "a field is bound but isn't an On/Off pair" (validation message, naming the offending field via `Visual_Validation_OnOffRequired`'s `{0}`) via `showSection()`, which shows exactly one of the frame/message/landing elements. The landing page (`buildLandingPage()`) mirrors the host's own empty-state look — an info icon (hand-built `SVGElement`s) plus heading, a divider, a greyed-out skeleton of a three-row group with the lower rows indented (`@keyframes toggle-slicer-skeleton-pulse`, disabled under `prefers-reduced-motion`), and a hint naming the accepted value formats and the one-field-per-toggle model.
- **Starter-DAX guide:** `buildLandingGuide()` adds a copyable step-by-step guide below the hint, as two ARIA tabs (a roving-tabindex tablist: arrows/Home/End move and select; selection is in-memory only, defaulting to **One toggle**). **One toggle** is a one-column `DATATABLE`, its measure and "drag the column into Toggles" (`SINGLE_TABLE_DAX`/`SINGLE_MEASURE_DAX`); **Toggle group** is the CROSSJOIN group table, a per-toggle measure, "drag each column in", then the optional Group enable column and gated measure (`TOGGLE_TABLE_DAX`/`TOGGLE_MEASURE_DAX`/`GROUP_GATE_DAX`). The constants in `visual.ts` match README's DAX verbatim - change them together. Example names are deliberately generic placeholders (`Toggle Table`/`Toggle`/`Toggle State` for one toggle; `Toggle Group Table`/`Toggle 1`-`3`/`Toggle 1 State`/`Group Enable`/`Toggle 1 Active` for a group) so it's obvious what is a name to replace and what each object is for; keep them that way. The resjson step text says to rename the columns, and the Group enable step says what it is for (greys the toggles out without resetting them; gate measures to make the numbers follow it). `docs/appsource/sample-report-spec.md` and the marketing screenshots use realistic demo content on purpose. It's hidden until the `@container toggle-slicer (min-width: 260px) and (min-height: 200px)` query in `visual.less` reveals it (and widens `.toggle-slicer__landing`'s `max-width`, again to 420px at `min-width: 440px` so the CROSSJOIN lines sit unscrolled); code blocks scroll sideways and the landing page scrolls vertically if it still doesn't fit. `copyToClipboard()` tries the async Clipboard API first and falls back to a hidden-textarea-plus-`execCommand("copy")` approach - some sandboxed iframe contexts allow one but not the other - and the clicked button's label briefly confirms "Copied!"/"Copy failed" either way.
- **Tooltip:** wired manually per row via `host.tooltipService` (pointerenter/pointermove/pointerleave on each switch), showing the row's name and current state ("Mixed" for a partly-on master), since this visual has no measure role for the host to build one from. `capabilities.json` sets `tooltips.supportedTypes.default: false` to make that explicit.
- **Responsive sizing** is pure CSS via container queries (`container-type: size` on the root element) — state labels hide below a 120px width threshold, and toggles scale with the tile's height shared across rows (see Size below) — rather than reading `options.viewport` in TypeScript.
- **Show/hide labels:** `stateLabel.show` (a `ToggleSwitch` in the Format pane, default **off**) is applied in `render()` as an inline `display` style on the label elements, not a CSS class — inline styles always beat the stylesheet's container-query rule, so this Format-pane override reliably wins regardless of the visual's current size, and setting it back to `""` (not toggling a class) cleanly restores the size-based auto-hide behaviour. The switch's `aria-label` always names both states regardless of this setting, since a report author hiding the visible labels makes the accessible name more important, not less.
- **State Label position and spacing:** `stateLabel.position` (an `ItemDropdown`, default `"inside"`; the card's Show toggle defaults off, and the default font is Arial 10px regular) toggles one of three mutually exclusive classes (`toggle-slicer--inline-left`/`--inline-right`/`--stacked`) on each row's cell (`.toggle-slicer`) in `renderSwitch()`. All show only the label matching that row's current state (a Mixed master shows neither); CSS `order` on `.toggle-slicer__label` keeps whichever one is visible on the correct side, since the On label otherwise comes after the switch in DOM order. `stateLabel.spacing` is written to `--toggle-label-gap` on each cell. **Inside switch** (`"inside"`, toggle skin only - a checkbox/radio row falls back to `"inline-right"`) adds `is-inside` to the switch, and the text is **stationary with the handle wiping it**: each state's text sits in its own `.toggle-slicer__layer` *under* the handle (built in `buildRow()` inside the track, `aria-hidden`), the On text centred in the left part of the track `[0, track − reach]` and the Off text in the right part `[reach, track]`, where `--toggle-reach` is the handle's far edge measured from its own end (the toggle's padding plus the handle's size), so each text is centred horizontally and vertically in the part of the track the handle isn't covering when that state is current. Each layer is clipped (`clip-path: inset()`) to the side of the handle it belongs to - empty when its state isn't current, the whole free part when it is - and the clip transitions with the same 0.15s ease-in-out as the handle's own slide, so the handle wipes the old text out and uncovers the new text while the text itself never moves (a Mixed master shows neither). The layer's text box shares the State Label's padding, border, radius and font. A hidden sizer, `.toggle-slicer__inner` (both labels overlaid in one grid cell, same box), gives the track its width - `2 × border + reach + the wider label`, never narrower than the 2:1 `--toggle-track-width` - so the width never changes on click and rows sharing the same two labels match. The switch then drops its fixed 2:1 width for `width: auto`, and the handle moves with `left: calc(100% - knob size - padding)` instead of the fixed `translateX` (Mixed: halfway). The font size is capped at 60% of the toggle's height so the text always fits; Off text uses the State Label font colour over the Off fill, On text the handle's On colour over the On fill. `StateLabelCardSettings.onPreProcess()` hides Spacing while Inside switch applies (the model wires `isToggleStyle()` to the Toggle card, since a checkbox/radio falls back to Right and still needs it). Where each row sits within the group is `toggleGroup.rowAlignment`'s job (see Row layout above).
- **Allow Interactions:** `interactionsAllowed()` checks `host.hostCapabilities.allowInteractions` (only an explicit `false` disables it — it's `undefined` in the common, unrestricted case). Both `handleToggleClick()` and `handleContextMenu()` no-op when interactions are disallowed (e.g. Focus mode thumbnails, some export/embed contexts), and `render()` reflects it visually via an `is-readonly` class (default cursor, reduced opacity) and by pulling the switch out of the tab order (`tabindex="-1"`), rather than leaving a focusable control that silently does nothing when activated.
- **Bookmarks / external filter changes:** state is recomputed from `options.jsonFilters` on every `update()` (`readStatesFromFilters()`), which the host re-runs whenever the visual's filter changes from outside — applying a bookmark, Sync slicers, or "reset to default". No selection-manager callback is needed since state isn't a selection.
- **Context menu:** a `contextmenu` listener on each switch calls `selectionManager.showContextMenu()` with the identity of the category row matching that toggle's current state (`identityFor()`, built from the first cross-joined row holding that value). The master row has no field, so it passes an empty identity - the SDK's own sample does the same - which still gives the host's general menu. Gated behind `interactionsAllowed()` and `isDisabled()` - the menu's filter/drill actions would otherwise bypass Group enable.
- **Knob centring:** `.toggle-slicer__knob` in `visual.less` is positioned at `top: 0; left: 0`, not `2px`/`2px` — its containing block is `.toggle-slicer__track`'s padding box, which is already inset by the track's own border, so an extra fixed offset there double-counted that border and pushed the knob past centre (flush with the bottom/right edge instead of centred). Keep that relationship (knob size = track size − 2 × border) if either is changed, and recompute the "on" state's `translateX` (track content width − knob width) to match.
- **Toggle border, padding and radius:** the Toggle card's Border group (`toggleControl.borderStyle`/`borderColor`/`borderWidth`) draws a ring around the track only once a style is chosen - `--toggle-border-width` is 0 until then, and high contrast forces 2px so the toggle keeps an outline against the theme's background. The handle's size is derived, not set: `--toggle-knob-size = trackHeight − 2 × effective border − 2 × effective padding`, positioned at `top/left: effective padding` inside the track's padding box (already inset by the border), so it stays centred at any combination. The "on" `translateX` needs no border or padding terms - both ends are inset the same amount, so they cancel and it is always `trackWidth − trackHeight`. The *effective* values cap the raw settings so the handle is never smaller than 2px even for extreme combinations (e.g. an 8px-tall toggle with a 6px border): `--toggle-effective-border-width = min(border, H/2 − 1px)` and `--toggle-effective-padding = min(padding, (H − 2 × border)/2 − 1px)`, declared on `.toggle-slicer__switch` next to `--toggle-track-height`. Corner radius is a percentage of the toggle's height (`--toggle-radius = H × pct / 100`; a checkbox has its own `--tg-checkbox-radius-pct`, a radio is always 50%). Until the report author sets one, the pane shows the style's own default (50 for Toggle, 20 for Checkbox): `update()` sets `ToggleCardSettings.radiusIsCustom` from the raw object and `onPreProcess()` swaps in `TOGGLE_RADIUS_DEFAULTS[skin]` while it is false - the same raw-object trick as `onColor`. **Handle card:** Color is the knob's, radio dot's and checkmark's colour (high contrast uses the theme foreground); Border and Corner radius (a percentage of the handle's size, 50 = circle) shape the knob or dot and are hidden for a checkbox, whose tick has no outline; Padding is a percentage of the toggle's height (default 18, so the dot and tick scale with the toggle) and insets the radio dot and the checkmark: `--toggle-dot-size = max(4px, 100% − 2 × (toggle padding + handle padding))`, with the tick's box 30% larger because its drawing has margin built into its viewBox. It is hidden for the toggle style, whose knob is sized by the toggle's padding. The track and handle take Embossed/Sunken shading from `--toggle-border-shadow`/`--hd-border-shadow`, composed with the 3D effect's own shadow variable (`--toggle-depth-shadow`/`--hd-base-shadow`) rather than overriding it.
- **3D depth effect:** `toggleControl.depthEffect` (default off, Format-pane label "3D effect") toggles an `is-depth` class on the switch in `render()`. The CSS layers a sheen gradient plus an inset groove-shadow on the track, and a sheen plus a stronger drop shadow on the knob (deepening further on hover), giving a raised/glossy skeuomorphic look. These use plain `rgba()` gradients rather than `color-mix()` — the latter needs a newer Chromium than every managed WebView2/Edge install is guaranteed to have — so the effect layers over whatever solid on/off colour is already set without needing to know its hue.
- **Control style (checkbox and radio skins):** `toggleControl.controlStyle` (`"toggle"`/`"checkbox"`/`"radio"`, default `"toggle"`) is resolved per row by `skinFor()` - header rows (master, Group enable) are never radios, so under the radio skin they're drawn as checkboxes (the conventional "select all"/"enable" control above a radio list). `renderSwitch()` toggles `is-checkbox`/`is-radio` and sets `role`: `"switch"` for the toggle skin, `"radio"` for a radio-skinned row only when Only one active is on (the toggle rows' own wrapper, `childrenEl` - `.toggle-group__children`, `display: contents` so it still shares groupEl's grid - then gets `role="radiogroup"` and a roving tabindex with one Tab stop on the checked radio; the checkbox-drawn header rows sit outside it in groupEl as ordinary Tab stops, and `placeRows()` only re-parents rows when headers are added/removed, since moving an element blurs it), otherwise `"checkbox"` - a radio drawn in an independent group behaves like a checkbox, so it isn't announced with radio semantics it doesn't have. `aria-label` picks `Visual_Switch_AriaLabel`/`Visual_Checkbox_AriaLabel`/`Visual_Radio_AriaLabel` to match the role. All skins share the same `.toggle-slicer__track`, so colour, border and the `is-depth` treatment apply unchanged - that's what "same flat and fancy styles as toggle and checkbox" means in practice. Checkbox: a rounded square (`width` pinned to `--toggle-track-height`), knob hidden, and `.toggle-slicer__checkmark` (built in `buildCheckmarkIcon()`) showing a tick when On or a dash when Mixed. Radio: a circular track, with the **toggle skin's own knob reused as the centre dot** - centred via `inset: 0; margin: auto` at 50% size, scaling in on `is-on` instead of translating - so the dot inherits the knob's colour and depth sheen with no extra rules. Every row always has both the knob and the checkmark in its DOM; switching skins only toggles classes.
- **Hover feedback:** `.toggle-slicer__switch:hover:not(.is-readonly):not(.is-disabled)` adds a soft `drop-shadow` only - no movement - as baseline pressable affordance (like the `:focus-visible` ring, not user-configurable), cleared under `prefers-reduced-motion`. Clicking a row's **name** also toggles it (like a native `<label>`), a bigger hit target for the small checkbox/radio skins.
- **Keyboard:** Space/Enter activate the focused row (`handleKeyDown()`); arrow keys and Home/End move **focus only** between enabled rows (inside a radiogroup, only among the radios - or only among the headers, from a header) - activating still takes Space/Enter, so browsing a radio group never silently rewrites the report's filters. Every enabled row is its own Tab stop, except in a radiogroup (roving tabindex, see Control style).
- **Custom title:** `groupLabel.text`/`position`/`alignment`/`spacing` render a static heading (`titleEl`, wrapped with the group (`groupEl`) in `titleWrapEl`, itself inside `frameEl`) that this visual draws itself — distinct from Power BI's own native visual title (Format → General → Title), which is host-rendered chrome outside this visual's control and can only be Left/Center/Right-aligned in a fixed top strip. `position` (`"inline-left"`/`"inline-right"`/`"above"`, default `"above"` since the group conversion - a heading over a list reads like a fieldset legend; stacked, the title's `text-align` follows the title alignment rather than centring) toggles a class on `titleWrapEl` mirroring the on/off labels' own scheme one level out, since the title's text never changes with the switch's state (unlike the on/off labels): `"inline-left"` needs no override (`titleEl` already comes before `container` in DOM order), `"inline-right"` sets `order: 1` on `.toggle-slicer__title` (`toggle-slicer-wrap--inline-right`) to flip it after the switch instead, and `"above"` (`toggle-slicer-wrap--stacked`) stacks them in a column with the title always first/top regardless of left/right (there's no horizontal axis to flip there). `showSection()` shows/hides `frameEl`. `alignment` (an `ItemDropdown`: Left/Center/Right/Justify, default `"left"`) positions titleWrapEl itself within the tile via a CSS auto margin on `titleWrapEl` (`is-title-align-left`/`-center`/`-right`: `margin-right`/both/`margin-left: auto`; Center with position Above also sets `align-items: center` and a centred title, reproducing the pre-group single toggle's title-over-switch look once `toggleLabel.show` is off - visible names widen the group being centred) — applied to `titleWrapEl` itself rather than `target`'s (`.toggle-slicer-visual`'s) own `justify-content`, since `target` is also the parent of the unrelated landing-page/validation-message sections (only shown via `showSection()` when `render()` never runs at all - an unbound field or a validation failure) and a class left on `target` from a previous successful render would otherwise still apply to whichever of those is showing on a later `update()`. `"justify"` sets `titleWrapEl` to `width: 100%; height: 100%; justify-content: space-between;`, spreading its two children (the title, and the switch+label group) to opposite ends along whichever axis is titleWrapEl's main axis - horizontally when `position` is Inline, vertically when it's Above - rather than leaving them shrink-wrapped together in the middle (the previous, and now-removed, hardcoded always-centred default). `text`'s own static default (in `settings.ts`) is blank, **not** `"Toggle group"` — that text is a resjson key (`Visual_GroupLabel_Text_Default`), resolved in `render()` only when `hasCustomTitleText` (computed once per `update()` against the raw `dataView.metadata.objects.groupLabel.text`, the same "check the raw object, not the populated model" trick `onColor` uses) is false, i.e. the property has no persisted value yet. This is what makes the title localized *and* on by default - the card's own `groupLabel.show` header toggle (default on) hides it outright, and clearing the text to a blank-but-persisted value hides it too. A hardcoded English default in `settings.ts` would have shown untranslated runtime text in every non-`en-US` report until a report author happened to touch the field, unlike `onText`/`offText`'s own placeholders, which a report author is expected to retype immediately. `text`'s `placeholder` (Format-pane-only, not rendered in the visual) still says `"Toggle group"` in plain English, matching that same `onText`/`offText` convention.
- **Font customization:** `groupLabel.font`/`fontColor`, `toggleLabel.font`/`fontColor` (row names) and `stateLabel.font`/`fontColor` (On/Off state text) are each a `FontControl` (family/size/bold/italic/underline as one composite Format-pane row) plus a separate `ColorPicker`, independently applied via `applyFonts()` as CSS custom properties (`--toggle-title-font-*`/`--toggle-name-font-*`/`--toggle-label-font-*`) consumed by `.toggle-slicer__title`/`.toggle-group__name`/`.toggle-slicer__label` in `visual.less`. Each `font-family` puts the variable *first in* a fallback stack (`var(--toggle-name-font-family, "Segoe UI"), wf_segoe-ui_normal, ..., sans-serif`) rather than as the var's own fallback, so a family missing on the viewer's machine degrades to sans-serif rather than the browser's serif default. There's no host API for reading the report theme's actual typography (unlike colour's `host.colorPalette.getColor()` - `IVisualHost` only exposes `colorPalette`, nothing font-related), so the defaults (title Segoe UI 14px bold `#605E5C`, names Segoe UI 12px `#252423`, state text Arial 12px bold `#15284C`) are a static approximation of the look the visual has always had, not a live theme readout. `settings.ts`'s `fontControl()` helper builds all three with the same sub-property names (`fontFamily`, `fontSize`, `fontBold`, `fontItalic`, `fontUnderline`), which is safe because each card is its own capabilities object. `applyFonts()` forces both font *colours* (not family/size/weight - typography choices don't need it, only legibility does) to `host.colorPalette.foreground` when `isHighContrast` is active, the same substitution `applyColors()` already does for `--toggle-label-color` — without it, a custom Format-pane font colour would keep rendering even when the host is forcing a high-contrast palette specifically to guarantee legibility.
- **Size (height-driven, ratio-locked):** `toggleControl.sizeMode` (`"responsive"`/`"fixed"`, default `"responsive"`) is only ever a report author-facing control over the switch's **height** — width always follows at a fixed ratio - the original 44x22 (2:1) for the toggle skin via `--toggle-track-width: calc(var(--toggle-track-height) * 2)`, 1:1 for checkbox/radio (`width: var(--toggle-track-height)`), so there's no separate width setting to keep in sync. In Responsive mode, `--toggle-track-height` is `clamp(var(--toggle-min-height), calc(50cqh / var(--toggle-row-count)), var(--toggle-max-height))` - the tile's height shared across however many rows `render()` reports in `--toggle-row-count`, so a tall tile with many rows doesn't size each toggle as if it had the whole tile to itself in `visual.less` — `cqh` is a container query height unit, resolving against the nearest ancestor size container (`.toggle-slicer-visual`'s `container-type: size`), so the switch fluidly scales with the *visual's own* height between `toggleControl.minHeight`/`maxHeight` (defaults 16/22, reproducing the two discrete sizes this visual used to hard-switch between at a single container-height breakpoint, now as a fluid scale's floor/ceiling instead) rather than jumping between two fixed sizes at one threshold. `applySize()` in `visual.ts` only ever supplies those three bounds as CSS custom properties (`--toggle-min-height`/`--toggle-max-height`/`--toggle-fixed-height`, set on the root element) — the actual clamping/scaling math all lives in the stylesheet. `minHeight`/`maxHeight` are independent `NumUpDown`s (each just its own 8-200 bound), so `applySize()` sorts the pair (`Math.min`/`Math.max`) before writing them out, rather than trusting whichever field a report author happened to type the larger number into — `clamp()` silently gives its first (minimum) argument precedence when the bounds are reversed, which would otherwise make Max height mean nothing whenever Min was set above it. **Fixed mode** toggles an `is-size-fixed` class on every `.toggle-slicer__switch` (in `renderSwitch()`) that overrides `--toggle-track-height` to a single literal `toggleControl.fixedHeight`, ignoring the visual's own size entirely. The clamp formula is declared on `.toggle-slicer__switch` itself, not on `.toggle-slicer-visual` (the container element) — a size container's `cqh`/`cqw` units resolve to `0` on the container element itself (querying your own size is circular and explicitly disallowed by the spec), so it has to live on a descendant instead; the knob's size/`translateX` calc()s (see the border-width note above) pick up `--toggle-track-height`/`--toggle-track-width` via ordinary CSS custom-property inheritance from that same ancestor. `ToggleCardSettings.onPreProcess()` hides whichever of min/max-height vs. fixed-height doesn't apply to the current mode.

## Conventions

- TypeScript, using the `pbiviz new` default `tsconfig.json`. `strict` is intentionally left off: `powerbi-visuals-tools`' generated plugin wrapper (`.tmp/precompile/visualPlugin.ts`) passes an optional `options?` into `new Visual(options)`, which fails under `strictNullChecks` — that file is regenerated on every build, so it can't be patched in-repo.
- No external UI framework — plain DOM/SVG manipulation, keeping the bundle small since this is a single-purpose control.
- **Localization scope:** only `stringResources/en-US/resources.resjson` is shipped, covering every fixed string the visual itself renders or exposes: the landing page heading/hint/starter-DAX guide steps/Copy button (including its "Copied!"/"Copy failed" states and per-block aria-labels), the validation message, the "Mixed" state, the master label default, each row's `aria-label`, and all seven Format pane cards' (`toggleGroup`, `groupLabel`, `toggleControl`, `handle`, `toggleLabel`, `stateLabel`, `behavior`) and their groups' names plus all property display names/descriptions. Add further `stringResources/<locale>/resources.resjson` files (and list them in `pbiviz.json`'s `stringResources` array) if this copy needs translating into another locale — do this with a reviewed translation, not a guessed one. `SINGLE_TABLE_DAX`/`SINGLE_MEASURE_DAX`/`TOGGLE_TABLE_DAX`/`TOGGLE_MEASURE_DAX`/`GROUP_GATE_DAX`'s DAX itself is a deliberate exception - it's literal code to paste verbatim, not natural-language UI text, same reasoning as the on/off label values below. Every `ItemDropdown`'s own item captions (`toggleControl.controlStyle`/`sizeMode`, `stateLabel.position`, `toggleLabel.position`, `toggleGroup.rowAlignment`/`verticalAlignment`, `groupLabel.position`/`alignment`, and every layer's `borderStyle` - e.g. "Left"/"Above", "Flat"/"Embossed"/"Sunken") are a second deliberate exception, left as plain English strings like `onText`/`offText`'s values — `IEnumMember.displayName` supports a resource-provider function, but wiring that up isn't worth it while the project ships only `en-US`.
  - Runtime strings (landing page, validation, tooltip, aria-label) go through `host.createLocalizationManager().getDisplayName(key)`, called directly in `visual.ts`.
  - Format pane strings go through the same mechanism, but indirectly: `settings.ts`'s cards/slices set `displayNameKey`/`descriptionKey` (not literal `displayName`/`description`) from `formattingSettings.SimpleCard`/`SimpleSlice`'s built-in localization support, and `FormattingSettingsService` only resolves those keys if it's constructed with a localization manager — see the `new FormattingSettingsService(this.localizationManager)` call in `visual.ts`'s constructor. Passing a plain `new FormattingSettingsService()` (no argument) here would silently make `displayNameKey`/`descriptionKey` inert. Note `capabilities.json`'s own `objects.*.properties.*.displayName`/`description` text is a separate, non-localizable schema declaration used as documentation/fallback shape — it's `settings.ts`'s copy (via the resjson) that actually renders in the Format pane, so keep all three in step: every property in `settings.ts` needs a same-named property in its `capabilities.json` object, and every `displayNameKey`/`descriptionKey` needs a resjson entry (card/group keys are `Visual_Card_*`/`Visual_Group_*`; slices are `Visual_<Card>_<Property>_DisplayName`/`_Description`, except the shared box properties, which are `Visual_Box_*`; a `FontControl` only has `_DisplayName`).
  - `ILocalizationManager.getDisplayName()` is a plain key lookup with no format-argument support, so `Visual_Switch_AriaLabel`/`Visual_Checkbox_AriaLabel`/`Visual_Radio_AriaLabel` are `{0}` (row name)/`{1}` (off)/`{2}` (on)/`{3}` (current) templates resolved manually in a single `.replace()` pass in `renderSwitch()` (so report-authored text containing a token like `{2}` is never re-substituted), and `Visual_Validation_OnOffRequired`'s `{0}` (field name) likewise in `update()` — keep those tokens intact (and reorder them, not the surrounding words, if a translation needs different word order) rather than concatenating separately-localized fragments, which would hard-code English word order into every locale.
  - The user-configurable on/off *label values* (`stateLabel.onText`/`offText`'s actual text, e.g. "On"/"Off", and their placeholders) are intentionally **not** part of this mechanism — they're already per-report-customizable Format-pane text properties, which is the more direct way to handle multilingual report content. Only the property *names* shown in the Format pane are localized, not the values a report author types into them.
  - Row *names* are the bound fields' own display names (renamed per visual in the field well), and the master row's `behavior.masterLabel` follows the title's pattern: blank static default, localized `Visual_MasterLabel_Default` ("All") shown until the raw dataView object has a persisted value (`hasCustomMasterLabel`).
  - `capabilities.json`'s `dataRoles[*].displayName`/`description` ("Toggles", "Group enable") appear in the Fields well, a UI surface the SDK does not offer a code-level localization hook for — this is a known, unavoidable gap, not an oversight.

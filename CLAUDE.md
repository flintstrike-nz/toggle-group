## Project Overview

A custom Power BI visual: a two-state (on/off) toggle switch used to drive a DAX-based filter toggle in Power BI reports. It replaces a standard slicer styled to look like a switch, giving a cleaner, purpose-built end-user control for a pattern that gets reused across multiple reports.

**Owner context:** Built by a Health Data Analyst Business Partner at Health New Zealand | Te Whatu Ora, for use in internal Power BI reporting.

## How It Works

The visual is bound to a single categorical data role (`ToggleTable[Toggle]`) from a disconnected table in the host report's data model:

```
ToggleTable = DATATABLE(
    "Toggle", STRING,
    "Value", INTEGER,
    {
        {"On", 1},
        {"Off", 0}
    }
)
```

The visual uses the SDK's `SelectionManager` to select/deselect the "On" or "Off" row exactly as a native slicer would — this means it applies a real filter on `ToggleTable[Toggle]`, and any report measure using:

```
ToggleState = SELECTEDVALUE(ToggleTable[Value], 0)
```

continues to work unchanged. **The visual is a rendering layer on top of the existing slicer-selection model — it does not use `persistProperties` for state, because that would not be readable by DAX.**

The bound column's two values don't have to be literally "On"/"Off" text — `ON_VALUES`/`OFF_VALUES` in `visual.ts` (matched case-insensitively, trimmed, via `normalize()`) also accept `"true"`/`"false"` and `"1"`/`"0"`, since a report author's own disconnected table may use a different convention (e.g. a `BOOLEAN` or `INTEGER` column instead of `STRING`). Whichever one row matches an On alias and the other an Off alias is what the validation requires — mixing conventions across the two rows (e.g. `"On"`/`"0"`) is fine, since each row is checked independently.

## Key Files

| File | Purpose |
|---|---|
| `capabilities.json` | Declares the single categorical data role, data view mapping, formatting `objects` — `toggleSettings` (on/off colour, on/off label, show-labels, label-position, label-spacing, show-background, background-colour, show-border, border-colour, border-width, depth-effect), `titleSettings` (title text, position, spacing), and `sizeSettings` (mode, min/max/fixed height) — and top-level feature flags (`supportsKeyboardFocus`, `supportsSynchronizingFilterState`, `supportsLandingPage`, `tooltips`) |
| `src/visual.ts` | Main `IVisual` implementation — constructor sets up `host`, `selectionManager`, `localizationManager`, `tooltipService`, and the switch DOM; `update()` reads current selection state and renders (or shows the landing page / validation message); click handler toggles selection |

| `stringResources/en-US/resources.resjson` | Localizable strings for the visual's own UI copy (landing page, validation message, tooltip label) — see Conventions for scope |
| `pbiviz.json` | Visual metadata (name, GUID, version, icon) |

## Implementation Notes

- Keep formatting (colours, labels) in `capabilities.json` `objects` and read them via `dataView.metadata.objects` in `update()` — don't hardcode colours in `visual.ts`, so users can theme it per-report from the Format pane.
- Only one row should ever be selected at a time — enforce single-select behaviour explicitly in the click handler (clear existing selection before selecting the new target) rather than relying on default SDK behaviour.
- Handle the "nothing selected" render state (first load, before any interaction) by defaulting the visual's initial render to match whatever `SELECTEDVALUE`'s fallback value is set to in the report's DAX, so the switch never visually contradicts the measure's default.
- Test with the disconnected `ToggleTable` pattern specifically — this visual assumes the bound column is unrelated to the rest of the model. It is not intended to filter a connected fact table directly.
- The `toggle` role's `dataReductionAlgorithm` in `capabilities.json` is capped at 100 rows, not 2 — capping it at exactly 2 would make the "must contain exactly one On row and one Off row" validation in `update()` unable to ever see more than 2 rows, silently truncating a mis-bound field (e.g. a real column with several distinct values) down to whichever two rows happen to come back, defeating the check it's meant to run.
- `handleToggleClick()` guards against overlapping clicks with an `isToggling` flag (cleared in a `finally`) since it's `async` — without it, two rapid clicks each read `this.isOn` before the first one's `clear()`/`select()` resolves, letting both racing calls flip and render inconsistent state.
- **High contrast:** `applyColors()` in `visual.ts` checks `host.colorPalette.isHighContrast` and, when active, substitutes the theme's `foreground`/`background`/`foregroundSelected` colours for the user's chosen on/off colours (via CSS custom properties), since custom Format-pane colours aren't guaranteed to be legible in high-contrast themes. It also forces the background transparent in this branch regardless of `showBackground`, for the same legibility reason.
- **On colour follows the theme by default:** `toggleSettings.onColor`'s value in `settings.ts` (`#2ECC71`) is only the fallback used before a report author ever touches the swatch. `applyColors()` checks the raw `dataView.metadata.objects.toggleSettings.onColor` (not the populated settings model, which always has *some* value and can't distinguish "never set" from "explicitly set to the default") — when it's absent, the effective On colour is `host.colorPalette.getColor("toggleOnColor").value` instead, i.e. the report theme's first data colour, matching the "Color 1" swatch under Format → Theme → Colors. This is the only `getColor()` call this visual makes, so it deterministically resolves to palette index 0 rather than round-robining to a later theme colour.
- **Background:** `toggleSettings.showBackground` (default off, so the visual shows through the report's own card/canvas background — see `applyColors()`) and `showBackground`'s conditionally-visible sibling `backgroundColor` set `this.target`'s inline `background-color` directly rather than a CSS class, since the fill is an arbitrary user colour rather than a fixed set of states. `ToggleSettingsCardSettings.onPreProcess()` in `settings.ts` hides the `backgroundColor` swatch in the Format pane whenever `showBackground` is off, so there's no colour picker that silently does nothing. Their Format-pane labels are "Show **switch** background"/"Switch background colour", not just "Background" — every visual (native or custom) also gets Power BI's own native General → Background automatically, which this code has no access to and can't affect either way; without the "switch" qualifier, a report author toggling one while looking at the other would see no change and reasonably conclude the control is broken.
- **Sync slicers / Filters pane:** `capabilities.json` declares a `general.filter` object plus `supportsSynchronizingFilterState: true` — the same contract native slicers use — so the toggle's selection can be synced across report pages via the Sync Slicers pane. No extra code is needed beyond the `SelectionManager` usage already in place.
- **Landing page vs. validation message:** `update()` distinguishes "no field bound yet" (landing page, shown via `supportsLandingPage: true`) from "a field is bound but its values aren't exactly one On/Off row" (validation message) via `showSection()`, which shows exactly one of the switch/message/landing elements at a time. The landing page (`buildLandingPage()`) mirrors the host's own generic "Select or drag fields..." empty-state look — an info icon (hand-built `SVGElement`s, not an image asset) plus heading, a divider, a greyed-out skeleton preview of the switch (`@keyframes toggle-slicer-skeleton-pulse`, disabled under `prefers-reduced-motion`), and a compact hint naming the accepted value formats up front rather than only surfacing them once a report author already hits the validation message.
- **Starter-DAX guide:** `buildLandingGuide()` adds a copyable step-by-step guide (create `ToggleTable`, then the `ToggleState` measure, matching this file's own documented DAX verbatim - see `TOGGLE_TABLE_DAX`/`TOGGLE_MEASURE_DAX` in `visual.ts`) below the landing page's existing hint. It's hidden until the `@container toggle-slicer (min-width: 260px) and (min-height: 200px)` query in `visual.less` reveals it (and widens `.toggle-slicer__landing`'s `max-width` to fit its longest line) - a report author is likely to have the visual resized larger while actively wiring up field bindings, but a small/default-dropped tile keeps just the existing compact hint rather than crowding it out. `copyToClipboard()` tries the async Clipboard API first and falls back to a hidden-textarea-plus-`execCommand("copy")` approach if it throws - some sandboxed iframe contexts (which is how this visual always runs) allow one but not the other - and the clicked button's own label briefly confirms "Copied!"/"Copy failed" either way rather than failing silently.
- **Tooltip:** wired manually via `host.tooltipService` (pointerenter/pointermove/pointerleave on the switch) rather than the host's automatic default tooltip, since this visual has no measure role for the host to build one from. `capabilities.json` sets `tooltips.supportedTypes.default: false` to make that explicit.
- **Responsive sizing** is pure CSS via container queries (`container-type: size` on the root element) — labels hide below a width threshold and the switch itself shrinks below a height threshold — rather than reading `options.viewport` in TypeScript.
- **Show/hide labels:** `toggleSettings.showLabels` (a `ToggleSwitch` in the Format pane, default **off**) is applied in `render()` as an inline `display` style on the label elements, not a CSS class — inline styles always beat the stylesheet's container-query rule, so this Format-pane override reliably wins regardless of the visual's current size, and setting it back to `""` (not toggling a class) cleanly restores the size-based auto-hide behaviour. The switch's `aria-label` always names both states regardless of this setting, since a report author hiding the visible labels makes the accessible name more important, not less.
- **Label position, alignment and spacing:** `toggleSettings.labelPosition` (an `ItemDropdown`, default `"inline-left"`) toggles one of three mutually exclusive classes (`toggle-slicer--inline-left`/`--inline-right`/`--stacked`) on the container in `render()`. All three now show only the label matching the current state (the other is hidden the same way `showLabels: false` hides both) — `"inline-left"`/`"inline-right"` put it to the left/right of the switch respectively, `"above"` (`--stacked`) centres it above the switch instead; CSS `order` on `.toggle-slicer__label` under each modifier is what keeps whichever one is visible on the correct side, since the On label otherwise comes after the switch in DOM order (and the Off label otherwise comes before it, wrong for `"inline-right"`). This replaced the previous two-item `"inline"`/`"above"` list, whose `"inline"` value showed *both* On/Off labels flanking the switch at once — a report author wanting that look back can't get it from this control anymore, only ever one label at a time, matching `"above"`'s original behaviour. A report saved before this rename can still have the old `"inline"` string persisted (a value falling out of a property's current `items` list doesn't get reset on its own), so `render()` reads both this and `titleSettings.position` through `normalizeLegacyInlinePosition()`, which maps a bare `"inline"` back to `"inline-left"` - without it, such a report's visible label would silently start flip-flopping sides with state (Off before the switch, On after it) instead of consistently sitting on one side, since `"inline"` no longer matches any of the three classList checks. `toggleSettings.alignment` (an `ItemDropdown`, default `"left"`) is a second, independent property controlling where the switch+label row itself sits: `"left"`/`"right"` only take effect within `--stacked` (`.toggle-slicer--stacked.is-align-left`/`-right`, via a CSS cross-axis auto margin overriding `align-items: center`) — outside `--stacked` this row shares titleWrapEl's own row with the title, and an auto margin there would consume free space *before* `titleSettings.alignment: justify`'s own `space-between` gets a chance to use it, silently breaking the far more common "just set the title's alignment to Justify" case. `"justify"` (`flex: 1 1 auto; justify-content: space-between;`) is left unscoped since flex-grow doesn't have that problem, but still only has a visible effect once this row's container is wider than its own shrink-wrapped content — i.e. `--stacked`'s own `align-self: stretch` (below) or `titleSettings.alignment: justify` stretching titleWrapEl - otherwise it's a harmless no-op. Since `"left"`/`"right"` only ever do anything at all when `labelPosition` is `"above"`, `ToggleSettingsCardSettings.onPreProcess()` hides the whole `alignment` property outside that mode instead of leaving a dropdown in the Format pane whose choices otherwise look like they do nothing - matching this file's own existing convention for `backgroundColor`/`borderColor`/`borderWidth`. `toggleSettings.labelSpacing` (a `NumUpDown` in px, default 8, matching the stylesheet's own default) is written to the `--toggle-label-gap` CSS custom property consumed by `.toggle-slicer`'s `gap`, in all three positions.
- **Allow Interactions:** `interactionsAllowed()` checks `host.hostCapabilities.allowInteractions` (only an explicit `false` disables it — it's `undefined` in the common, unrestricted case). Both `handleToggleClick()` and `handleContextMenu()` no-op when interactions are disallowed (e.g. Focus mode thumbnails, some export/embed contexts), and `render()` reflects it visually via an `is-readonly` class (default cursor, reduced opacity) and by pulling the switch out of the tab order (`tabindex="-1"`), rather than leaving a focusable control that silently does nothing when activated.
- **Bookmarks:** `selectionManager.registerOnSelectCallback()` is registered once in the constructor to resync `this.isOn` and re-render whenever selection changes without going through `handleToggleClick()` — applying a bookmark, another synced slicer changing the selection, or a report-level "clear all filters" action. Without this, `update()`'s own `isOnSelected()` recompute is the only thing keeping the switch in sync, which doesn't fire for every way selection can change.
- **Context menu:** a `contextmenu` listener on the switch calls `selectionManager.showContextMenu()` with the identity of the row the switch currently represents (whichever of on/off is active), giving the standard Power BI right-click menu (filter, drill actions, etc.) — gated behind the same `interactionsAllowed()`/valid-category checks as clicking.
- **Knob centring:** `.toggle-slicer__knob` in `visual.less` is positioned at `top: 0; left: 0`, not `2px`/`2px` — its containing block is `.toggle-slicer__track`'s padding box, which is already inset by the track's own border, so an extra fixed offset there double-counted that border and pushed the knob past centre (flush with the bottom/right edge instead of centred). Keep that relationship (knob size = track size − 2 × border) if either is changed, and recompute the "on" state's `translateX` (track content width − knob width) to match.
- **Border width and colour:** `toggleSettings.showBorder`/`borderColor`/`borderWidth` (default off, `#605E5C`, 2px) let a report author put a coloured ring around the track — outside `showBorder`, the border stays `transparent` (as before) but `borderWidth`'s px value is still applied, since it's load-bearing for knob centring, not just cosmetic. The knob's `width`/`height` in `visual.less` are `calc(trackHeight - 2 * var(--toggle-effective-border-width))` rather than a fixed px, so the knob stays exactly centred (and the border reads as an even ring around it) at any width the report author picks. The "on" state's `translateX` needs no equivalent calc() — algebraically, `(trackWidth - 2b) - (trackHeight - 2b) = trackWidth - trackHeight` regardless of the border width `b`, so it stays the same fixed px value it always was. `ToggleSettingsCardSettings.onPreProcess()` hides `borderColor`/`borderWidth` in the Format pane whenever `showBorder` is off. **`--toggle-effective-border-width`** (declared alongside `--toggle-track-height` on `.toggle-slicer__switch`) is `min(var(--toggle-border-width), calc(var(--toggle-track-height) / 2 - 1px))`, not the raw `borderWidth` value — `borderWidth`'s own range (0-6px) and the switch's height (8-200px via Size settings, below) are independently configurable, so an extreme combination (e.g. an 8px-tall switch with a 6px border) would otherwise drive the knob's calc() to zero or negative, collapsing it. Capping the border actually used in layout at just under half whatever the track height currently resolves to (Responsive's fluid value or Fixed's literal one) guarantees a knob at least 2px across no matter what a report author picks, without needing to restrict the two settings' own Format-pane ranges against each other.
- **3D depth effect:** `toggleSettings.depthEffect` (default off, Format-pane label "Make it fancy!") toggles an `is-depth` class on the switch in `render()`. The CSS layers a sheen gradient plus an inset groove-shadow on the track, and a sheen plus a stronger drop shadow on the knob (deepening further on hover), giving a raised/glossy skeuomorphic look. These use plain `rgba()` gradients rather than `color-mix()` — the latter needs a newer Chromium than every managed WebView2/Edge install is guaranteed to have — so the effect layers over whatever solid on/off colour is already set without needing to know its hue.
- **Control style (checkbox skin):** `toggleSettings.controlStyle` (an `ItemDropdown`, default `"toggle"`) toggles an `is-checkbox` class on the switch in `render()`, which also switches the element's `role` between `"switch"` and `"checkbox"` (a screen reader user shouldn't hear "switch" for a control drawn as a checkbox, and both roles support `aria-checked` identically, so nothing else about the accessibility wiring needs to branch on it). The switch's `aria-label` in `render()` also branches on `isCheckbox` between `Visual_Switch_AriaLabel`/`Visual_Checkbox_AriaLabel` (same `{0}`/`{1}`/`{2}` token contract, see `resources.resjson`) - the toggle-worded template's literal "... toggle, currently ..." phrasing would otherwise contradict `role="checkbox"` for a screen reader user, even though every other Format-pane setting genuinely doesn't care which skin is active. The checkbox skin reuses the exact same `.toggle-slicer__track` element as the toggle skin — only `border-radius` changes (a proportional rounded square via `calc(var(--toggle-track-height) * 0.2)` instead of the pill's `999px`) and its `width` is pinned to `var(--toggle-track-height)` instead of the toggle's 2:1 `--toggle-track-width`, so it comes out square at whatever height Size settings currently resolve to. Colour (`applyColors()`), border, and the `is-depth` "fancy" gradient/shadow treatment are all declared against `.toggle-slicer__track`/`.toggle-slicer__switch.is-depth` generically, so both skins pick them up unchanged with no extra branching — this is what "follows the same design language for flat and fancy" means in practice. In place of the toggle skin's sliding `.toggle-slicer__knob` (hidden via `display: none` under `is-checkbox`), a `.toggle-slicer__checkmark` SVG (hand-built in `buildCheckmarkIcon()`, same approach as `buildInfoIcon()`) fades and scales in on `is-on` instead of translating like the knob; it's coloured via the same `--toggle-knob-color-on` custom property the knob's "on" state already used, since the checkmark is only ever shown once "on". Both `.toggle-slicer__knob` and `.toggle-slicer__checkmark` always exist in the DOM regardless of the active skin — `render()` only toggles the `is-checkbox` class — so switching `controlStyle` back and forth doesn't need to create/destroy either element.
- **Hover feedback:** `.toggle-slicer__switch:hover:not(.is-readonly)` adds a soft `drop-shadow` only - no `transform`/movement, deliberately, so the switch stays put on hover - giving pressable-button affordance without a Format-pane setting to turn it off (like the existing `:focus-visible` ring, it's baseline behaviour, not user-configurable) — gated behind `is-readonly` the same way clicking already is, and cleared under `prefers-reduced-motion` alongside the track/knob transitions.
- **Custom title:** `titleSettings.text`/`position`/`alignment`/`spacing` render a static heading (`titleEl`, wrapped with the existing switch/label container in a new `titleWrapEl`) that this visual draws itself — distinct from Power BI's own native visual title (Format → General → Title), which is host-rendered chrome outside this visual's control and can only be Left/Center/Right-aligned in a fixed top strip. `position` (`"inline-left"`/`"inline-right"`/`"above"`, default `"inline-left"`) toggles a class on `titleWrapEl` mirroring the on/off labels' own scheme one level out, since the title's text never changes with the switch's state (unlike the on/off labels): `"inline-left"` needs no override (`titleEl` already comes before `container` in DOM order), `"inline-right"` sets `order: 1` on `.toggle-slicer__title` (`toggle-slicer-wrap--inline-right`) to flip it after the switch instead, and `"above"` (`toggle-slicer-wrap--stacked`) stacks them in a column with the title always first/top regardless of left/right (there's no horizontal axis to flip there). `position` is read through the same `normalizeLegacyInlinePosition()` helper as `toggleSettings.labelPosition` (see above), for the same reason - a report saved before the "inline"/"above" rename can still have the bare `"inline"` string persisted. `showSection()` shows/hides `titleWrapEl` (not `container` directly), since `container` moved a level deeper to make room for `titleEl`. `alignment` (an `ItemDropdown`: Left/Right/Justify, default `"left"`) positions titleWrapEl itself within the tile via a CSS auto margin on `titleWrapEl` (`is-title-align-left`/`-right`: `margin-right`/`margin-left: auto`) — applied to `titleWrapEl` itself rather than `target`'s (`.toggle-slicer-visual`'s) own `justify-content`, since `target` is also the parent of the unrelated landing-page/validation-message sections (only shown via `showSection()` when `render()` never runs at all - an unbound field or a validation failure) and a class left on `target` from a previous successful render would otherwise still apply to whichever of those is showing on a later `update()`. `"justify"` sets `titleWrapEl` to `width: 100%; height: 100%; justify-content: space-between;`, spreading its two children (the title, and the switch+label group) to opposite ends along whichever axis is titleWrapEl's main axis - horizontally when `position` is Inline, vertically when it's Above - rather than leaving them shrink-wrapped together in the middle (the previous, and now-removed, hardcoded always-centred default). `text`'s own static default (in `settings.ts`) is blank, **not** `"Toggle label"` — that text is a resjson key (`Visual_TitleText_Default`), resolved in `render()` only when `hasCustomTitleText` (computed once per `update()` against the raw `dataView.metadata.objects.titleSettings.text`, the same "check the raw object, not the populated model" trick `onColor` uses) is false, i.e. the property has no persisted value yet. This is what makes the title both localized *and* on by default without a separate `showTitle` toggle — a hardcoded English default in `settings.ts` would have shown untranslated runtime text in every non-`en-US` report until a report author happened to touch the field, unlike `onLabel`/`offLabel`'s own placeholders, which a report author is expected to retype immediately. `text`'s `placeholder` (Format-pane-only, not rendered in the visual) still says `"Toggle label"` in plain English, matching that same `onLabel`/`offLabel` convention.
- **Font customization:** `titleSettings.font`/`fontColor` and `toggleSettings.labelFont`/`labelFontColor` are each a `FontControl` (family/size/bold/italic/underline as one composite Format-pane row) plus a separate `ColorPicker`, independently applied via `applyFonts()` as CSS custom properties (`--toggle-title-font-*`/`--toggle-label-font-*`) consumed by `.toggle-slicer__title`/`.toggle-slicer__label` in `visual.less`. There's no host API for reading the report theme's actual typography (unlike colour's `host.colorPalette.getColor()` - `IVisualHost` only exposes `colorPalette`, nothing font-related), so the defaults (`"Segoe UI"`, 14px/bold for the title, 12px/regular for labels, both `#605E5C`) are a static approximation of this visual's own previous hardcoded look, not a live theme readout. `applyFonts()` forces both font *colours* (not family/size/weight - typography choices don't need it, only legibility does) to `host.colorPalette.foreground` when `isHighContrast` is active, the same substitution `applyColors()` already does for `--toggle-label-color` — without it, a custom Format-pane font colour would keep rendering even when the host is forcing a high-contrast palette specifically to guarantee legibility.
- **Size (height-driven, ratio-locked):** `sizeSettings.mode` (`"responsive"`/`"fixed"`, default `"responsive"`) is only ever a report author-facing control over the switch's **height** — width always follows at the original 44x22 ratio (2:1) via `--toggle-track-width: calc(var(--toggle-track-height) * 2)`, so there's no separate width setting to keep in sync. In Responsive mode, `--toggle-track-height` is `clamp(var(--toggle-min-height), 50cqh, var(--toggle-max-height))` in `visual.less` — `cqh` is a container query height unit, resolving against the nearest ancestor size container (`.toggle-slicer-visual`'s `container-type: size`), so the switch fluidly scales with the *visual's own* height between `sizeSettings.minHeight`/`maxHeight` (defaults 16/22, reproducing the two discrete sizes this visual used to hard-switch between at a single container-height breakpoint, now as a fluid scale's floor/ceiling instead) rather than jumping between two fixed sizes at one threshold. `applySize()` in `visual.ts` only ever supplies those three bounds as CSS custom properties (`--toggle-min-height`/`--toggle-max-height`/`--toggle-fixed-height`, set on the root element) — the actual clamping/scaling math all lives in the stylesheet. `minHeight`/`maxHeight` are independent `NumUpDown`s (each just its own 8-200 bound), so `applySize()` sorts the pair (`Math.min`/`Math.max`) before writing them out, rather than trusting whichever field a report author happened to type the larger number into — `clamp()` silently gives its first (minimum) argument precedence when the bounds are reversed, which would otherwise make Max height mean nothing whenever Min was set above it. **Fixed mode** toggles an `is-size-fixed` class on `.toggle-slicer__switch` that overrides `--toggle-track-height` to a single literal `sizeSettings.fixedHeight`, ignoring the visual's own size entirely. The clamp formula is declared on `.toggle-slicer__switch` itself, not on `.toggle-slicer-visual` (the container element) — a size container's `cqh`/`cqw` units resolve to `0` on the container element itself (querying your own size is circular and explicitly disallowed by the spec), so it has to live on a descendant instead; the knob's size/`translateX` calc()s (see the border-width note above) pick up `--toggle-track-height`/`--toggle-track-width` via ordinary CSS custom-property inheritance from that same ancestor. `SizeSettingsCardSettings.onPreProcess()` hides whichever of min/max-height vs. fixed-height doesn't apply to the current mode.

## Conventions

- TypeScript, using the `pbiviz new` default `tsconfig.json`. `strict` is intentionally left off: `powerbi-visuals-tools`' generated plugin wrapper (`.tmp/precompile/visualPlugin.ts`) passes an optional `options?` into `new Visual(options)`, which fails under `strictNullChecks` — that file is regenerated on every build, so it can't be patched in-repo.
- No external UI framework — plain DOM/SVG manipulation, keeping the bundle small since this is a single-purpose control.
- **Localization scope:** only `stringResources/en-US/resources.resjson` is shipped, covering every fixed string the visual itself renders or exposes: the landing page heading/hint/starter-DAX guide steps/Copy button (including its "Copied!"/"Copy failed" states and per-block aria-labels), the validation message, the tooltip label, the switch's `aria-label`, and all three Format pane cards' (`toggleSettings`, `titleSettings`, `sizeSettings`) names plus all property display names/descriptions. Add further `stringResources/<locale>/resources.resjson` files (and list them in `pbiviz.json`'s `stringResources` array) if this copy needs translating into another locale — do this with a reviewed translation, not a guessed one. `TOGGLE_TABLE_DAX`/`TOGGLE_MEASURE_DAX`'s DAX itself is a deliberate exception - it's literal code to paste verbatim, not natural-language UI text, same reasoning as the on/off label values below. The `labelPosition`/`titleSettings.position`/`sizeSettings.mode` dropdowns' own item captions ("Inline"/"Above", "Responsive"/"Fixed") are a second deliberate exception, left as plain English strings like `onLabel`/`offLabel`'s values — `IEnumMember.displayName` supports a resource-provider function, but wiring that up isn't worth it while the project ships only `en-US`.
  - Runtime strings (landing page, validation, tooltip, aria-label) go through `host.createLocalizationManager().getDisplayName(key)`, called directly in `visual.ts`.
  - Format pane strings go through the same mechanism, but indirectly: `settings.ts`'s cards/slices set `displayNameKey`/`descriptionKey` (not literal `displayName`/`description`) from `formattingSettings.SimpleCard`/`SimpleSlice`'s built-in localization support, and `FormattingSettingsService` only resolves those keys if it's constructed with a localization manager — see the `new FormattingSettingsService(this.localizationManager)` call in `visual.ts`'s constructor. Passing a plain `new FormattingSettingsService()` (no argument) here would silently make `displayNameKey`/`descriptionKey` inert. Note `capabilities.json`'s own `objects.toggleSettings.properties.*.displayName`/`description` text is a separate, non-localizable schema declaration used as documentation/fallback shape — it's `settings.ts`'s copy that actually renders in the Format pane, so that's the one kept in sync with the resjson.
  - `ILocalizationManager.getDisplayName()` is a plain key lookup with no format-argument support, so `Visual_Switch_AriaLabel` is a `{0}`/`{1}`/`{2}` template resolved manually with `.replace()` in `render()` — keep those tokens intact (and reorder them, not the surrounding words, if a translation needs different word order) rather than concatenating separately-localized fragments, which would hard-code English word order into every locale.
  - The user-configurable on/off *label values* (`toggleSettings.onLabel`/`offLabel`'s actual text, e.g. "On"/"Off", and their placeholders) are intentionally **not** part of this mechanism — they're already per-report-customizable Format-pane text properties, which is the more direct way to handle multilingual report content. Only the property *names* shown in the Format pane are localized, not the values a report author types into them.
  - `capabilities.json`'s `dataRoles[0].displayName`/`description` ("Toggle") appear in the Fields well, a UI surface the SDK does not offer a code-level localization hook for — this is a known, unavoidable gap, not an oversight.
